Chapter 1 — What the Platform is

This chapter explains what the Platform is, who it serves and which parts are built today. It is the first chapter of the System Owner's Handbook and is written for the product owner, who is a software engineer and needs a clear picture before reading the detailed chapters. It ends with a map of the 18 module chapters, so a reader can find any topic.

1.1 One paragraph summary

The Platform is a multi-tenant web application that runs the daily work of clinics. "Multi-tenant" means one running system serves many separate clinic businesses, and each business sees only its own data. One clinic business is an organization. An organization has one or more locations (branches). Staff log in, and what they see depends on their role and on the features the organization has switched on. The backend is a NestJS API with a PostgreSQL database. The front end is a React web app. Chapter 4 describes the stack, and Chapter 8 describes how tenants are kept apart.

1.2 What a clinic gets

A clinic uses the Platform to do these jobs:

  • keep a patient record, including clinical history, vitals, documents and signed consents (Chapter 28);
  • book appointments and manage the calendar (Chapter 29);
  • run a doctor-wise waiting line with tokens after the patient arrives (Chapter 30);
  • let the doctor work from one screen, the consultation workspace (Chapter 31);
  • write and print prescriptions (Chapter 32);
  • plan treatment in steps with a treatment plan (Chapter 33);
  • bill patients, take payments, issue invoices and close the cash counter (Chapter 34);
  • calculate doctor commission (Chapter 35), run reports (Chapter 36), manage employees (Chapter 37), payroll (Chapter 38) and inventory (Chapter 39);
  • send work to a dental lab and track it, including a separate lab portal for the lab (Chapters 40 to 42);
  • manage subscription and sign-up (Chapter 45).

1.3 Specialties: general, dental and others

An organization carries one or more specialty tags. The code lists six: general, dental, skin, ortho, physio and eye. The sign-up form offers them as choices, for example "Skin / dermatology", "Orthopaedics", "Physiotherapy" and "Eye care". The tags describe which features are relevant to a clinic.

What is general. Patients, appointments, the queue, consultation, prescriptions, treatment plans, billing, commissions, reports, employees, payroll and inventory work for any clinic type. Their feature keys carry the tag "general".

What is dental-specific. Two parts are built for dental clinics:

  • the teeth chart (FDI tooth numbering), whose feature patients.teeth_chart is tagged dental and ortho, and the "dental info" record of a patient;
  • the dental lab ordering and production flow, whose feature is dental.lab_orders, tagged dental and ortho. The Platform ships dental lab workflows (for example "Try-in stage" and "Complete denture" stage lists) as seed data for the workflow engine.

Honest summary. Dental is the most developed specialty. A clinic of another type can use every general module today. The tags for skin, ortho, physio and eye exist as labels, but this chapter found no screens or rules written only for skin, physio or eye care [Partial]. The workflow engine (Chapter 43) is designed so a new specialty can be added as data, not code, but only dental data is seeded.

2.2 Super admin

The super admin is the person who operates the Platform itself, not a clinic. They are exempt from the tenant checks, the feature check and the permission check.

Day to day. They create and review organizations, set which features each organization is entitled to (optionally with a trial end date), record subscription payments by hand in Subscriptions, manage the shared Lab Directory, and edit forms, workflows and stage templates in Config Studio.

Sidebar. Organizations, Subscriptions, Lab Directory, and the Config Studio group with Form schemas, Workflows and Stage templates. These five entries are marked super admin only in the registry. They also see the clinic entries when they are working inside an organization.

Cannot do. Nothing is blocked by permission. In practice a super admin has no clinic role, so clinic-facing personal screens such as a doctor's own earnings have no staff record behind them.

2.3 Owner

The owner is the person who owns one organization. The owner has no role record: they get every permission at its widest scope, and permissions are still dropped when their feature is not active.

Day to day. Setting up the clinic and watching it: Locations, User Admin (staff logins), and the four setup pages Roles & permissions, Features (switch features on or off within what the super admin granted), Sidebar and Theme. They can also use every clinic module.

Cannot do. The owner cannot reach the five platform-only pages, cannot enable a feature that is not entitled, and cannot create permissions that do not exist in the catalog.

2.4 The five system roles

Every organization is seeded with five system roles: Admin, Doctor, Receptionist, Assistant and Accountant. They are read-only templates; to change one, the owner clones it into a custom role.

Admin. Runs the clinic day to day. It holds the Full bundle of every module except four clinical acts (conducting consultations, creating prescriptions, own queue, own earnings), but it can run and force-complete any doctor's queue. Home page: Dashboard. Uses: Dashboard, Clinic overview, Patients, Appointments, Billing, Reports, Employees, Payroll, Locations, User Admin and setup pages. Cannot: write prescriptions or conduct a consultation unless the owner clones Doctor for them.

Doctor. Consults patients. Home page: My Queue. A doctor sees only their own patients (scope own: people they have an appointment or queue entry with) and their own appointments. Day to day: start the queue, call the next patient, work in the consultation workspace, write and print prescriptions, create lab orders, check My earnings. Uses: My Queue, Patients, Appointments, Prescriptions, Lab orders, Order templates, My earnings, Clinic overview. Cannot: collect payments, see invoices, manage employees, change settings.

Receptionist. The front desk. Home page: Appointments. Day to day: register patients, book and reschedule, check patients in, add walk-ins on the reception queue board, run the TV display, collect payments, apply preset discounts. Uses: Patients, Appointments, Billing desk, Invoices, Payments, Lab orders. Cannot: read clinical notes, issue refunds, void invoices, give custom discounts, run reports.

Assistant. Chairside help. Home page: Appointments. Day to day: view patients at this location including clinical records, edit the teeth chart, book appointments, check patients in, view stock. Uses: Patients, Appointments, Lab orders. Cannot: take payments, write prescriptions, edit patient details.

Accountant. Money. Home page: Billing desk. Day to day: view and edit invoices, void them, issue refunds, close the cash counter, record expenses, see every doctor's earnings, read financial reports, manage lab billing and payables. Uses: Billing desk, Invoices, Payments, Expenses, Finance overview, Reports, Doctor earnings, Billing activity, Lab billing, Lab payables. Cannot: open patient clinical records, run the queue, book appointments.

The home page is where a user lands after login. If the user may not open it, the web app falls back to the Dashboard.

2.5 Custom roles

An owner (or a staff member with the roles permission) builds a custom role on the Roles & permissions screen. For each module the role gets None, Basic or Full, or an Advanced list of single permissions with a scope. A role also has a home page and members. Custom roles are the way to model a hygienist, a branch manager or a billing clerk. A holder of the roles permission cannot grant anything they do not hold themselves.

2.6 Lab-side users

Labs are separate from clinics. A lab has its own members, who sign in with a normal login but hold a lab membership instead of a clinic assignment. They see the Lab portal entry in the sidebar (marked for users with at least one lab membership).

  • Lab admin. Accepts or rejects a submitted order, asks the clinic a question (clarification), moves production steps, manages the lab team (add people, change roles, deactivate), and sees clinics, billing and profile.
  • Lab technician. Works the production steps (for example finishing an order into quality check and passing it). Cannot accept or reject orders in the seeded dental workflow, and cannot manage the team.
  • Magic-link contact. A person at the lab with no login. The clinic issues a magic link for one order. The link opens one page where the person can read the order, accept it, reject it with a reason or ask a clarification, within the link's expiry and use limit. Chapter 41 covers the lab portal in full.

These users cannot see anything inside a clinic apart from what the order and the clinic-lab link show them. The clinic decides how much patient identity the lab sees: full name or a code only.

2.7 Public and unauthenticated audiences

  • The TV display. A screen in the waiting room opens the display page for a location. It shows, per doctor, the token being served and the next few tokens. It needs no login and by design shows no patient names or phones. Managing the TV display from a screen is [Not implemented]: there is no admin page for it, and the receptionist role only holds the permission to manage it.
  • Visitors before login. Login, register, forgot password, reset password and verify email pages are public.
  • Patients. There is no patient portal [Not implemented]. Patients appear in the Platform only as records that staff create and as tokens on a ticket.

2.8 Limitations and known gaps

  • Sidebar labels per role in the table were deduced from permissions and the registry, not observed in a running app.
  • A staff member with no assignment at the active location gets no role permissions there, even if they hold a role elsewhere.
  • Super admins have no staff record, so screens built on the employee record do not apply to them.

3.1 Opening: sign in and start the queue

Receptionist R1 signs in. If R1 may work at more than one location, the app first asks which location to use (Chapter 8, the multi-tenant model). R1's role is Receptionist, so the home page is Appointments (Chapter 11, roles and permissions).

Dr. Example One signs in and lands on My Queue, the Doctor home page. Opening that page creates the doctor's queue session for today if it does not exist yet. A queue session is one doctor's waiting line for one clinic day at one location, and the clinic day follows the Main location's timezone, not the server's. The doctor clicks Start my queue. A new session begins in the state "Doctor not started": reception can already add patients, but nobody can be called until the doctor starts. The Queue chapter (Chapter 30) describes the states Doctor not started, Open and Paused.

Status: [Implemented]. Module: Queue.

3.2 A booking is made

Earlier, R1 opened Appointments and booked Sample Patient A with Dr. Example One. The booking form checks the chosen time slot live and suggests another time when the slot is taken. The booking is saved as an appointment. Booking is only about reserving a time; it does not create a queue entry. The Appointments chapter (Chapter 29) covers booking, rescheduling and the status changes of a booking. Reminders to the patient and online booking are [Not implemented].

Status: [Implemented]. Module: Appointments.

3.3 Arrival: check-in and token

Sample Patient A arrives. R1 finds the booking and clicks Check in, then Check in & get token. The Queue chapter (Chapter 30) explains that check-in is the moment the patient joins the doctor's line. The patient gets a token that belongs to Dr. Example One's queue for the day. A token is the short number printed on the ticket, such as "E-001": a letter prefix that comes from the doctor's name (or a prefix set on the doctor's assignment), then a three-digit counter. R1 clicks Print ticket in the success message, and the browser prints a small slip with the token, the doctor and roughly how many people are ahead.

If the patient has unpaid dues, a red "Rs … due" badge appears next to the patient in the queue, so R1 can ask about it (Billing, Chapter 34, feature "Show dues at check-in"). A person who arrives without a booking is a walk-in: R1 clicks Walk-in on the reception queue board, picks the doctor, and the patient gets a token the same way.

In the waiting room, the TV display shows the token being served and the next few tokens for each doctor. It needs no login and shows no patient names. The Platform pushes every change to the reception board, the doctor's screen and the TV live, through a realtime connection (Chapter 63).

Status: [Implemented]. Modules: Appointments (check-in) and Queue (token, board, TV).

3.4 The doctor's queue

Dr. Example One is on My Queue. The doctor clicks Call next. The button shows who will be called and why, for example "(E-001 · Appointment due)". The Queue chapter (Chapter 30) explains that a rule engine picks the next patient, either by smart rules or by first come, first served, depending on the clinic's setting (urgent patients go first in both modes). The called token flashes on the TV. When the patient walks in, the doctor clicks Patient is here — start.

If a called patient does not come, the receptionist or doctor can skip them, and they can rejoin later. A patient can also be sent for a test and return, or be transferred to another doctor. These actions are described in Chapter 30.

Status: [Implemented]. Module: Queue.

3.5 The consultation workspace

Starting the consultation creates the encounter, the clinical record of this one visit, and opens the consultation workspace at the consultation page. The Consultation chapter (Chapter 31) explains that the clinical record begins only when the doctor really starts, never at booking or check-in. In the workspace the doctor sees the patient at a glance, with allergy and medical alerts built from free-text fields (a structured allergy list is [Partial]), writes visit notes that auto-save, and records the treatments done today. The doctor can open the patient record without leaving the page.

The doctor does not see treatment prices unless the doctor's role holds the price permission; the default Doctor role does not.

Status: [Implemented]. Module: Consultation.

3.6 Prescription and printing

In the same workspace the Prescription panel lets the doctor search a medicine, set dose, frequency and duration, or choose a preset. The Prescriptions chapter (Chapter 32) explains the full module. The doctor clicks Sign & print. The Platform signs the prescription and shows a PDF preview on the clinic's print layout, with a Print button. Urdu text typed by the doctor is printed in Nastaliq script, right to left; the labels stay in English.

Status: [Implemented]. Module: Prescriptions.

3.7 Completing the visit

The doctor clicks Complete. The toast says "Visit completed" and the doctor returns to My Queue. At the same moment, in the same database transaction, the booked appointment becomes completed and the Platform creates charges for the visit: a consultation charge, plus one charge per treatment recorded in the encounter, priced from the clinic's price list. This happens only when the organization has the feature billing.invoices enabled. The Consultation chapter (Chapter 31) and the Billing chapter (Chapter 34) describe the automatic charges. No invoice exists yet: the charges wait on the Billing desk.

Status: [Implemented]. Modules: Queue (complete), Consultation, Billing (automatic charges).

3.8 A lab order

Sample Patient A needs a crown, so Dr. Example One orders it from Example Dental Lab. The doctor opens Lab orders, creates a lab order with an item (for example a zirconia crown), and submits it, so its status becomes Submitted. The Dental lab chapter (Chapter 40) covers the clinic side. In this version a lab order is not created from inside the consultation workspace and is not linked to an encounter [Not implemented], so the doctor orders it from the separate Lab orders page.

The lab sees the order in its own lab portal (Chapter 41). A lab admin there can accept it with an expected date, reject it with a reason or ask a question. Instead of an account, the lab can also receive a magic link for the single order: a link that opens one page where the person can accept, reject or ask a clarification without logging in. The clinic can copy that link. The code can also queue the link for delivery through the notification outbox when the lab has a contact number or email (Chapter 44); whether a WhatsApp message actually leaves the Platform is [Unverified], since notifications are in-app only. When the lab accepts, the order moves on, and its later stages are tracked through the workflow engine (Chapter 43).

Status: [Implemented], except that a lab order has no link to the consultation. Modules: Dental lab, Lab portal.

3.9 Collecting payment and the invoice

Sample Patient A goes to the front desk. R1 opens the Billing desk. The first section, Ready to bill, lists Sample Patient A with the count of charges and the unbilled amount. R1 clicks Bill, and the Collect payment sheet slides in. R1 can give a discount (the Receptionist role holds the permission for preset discount types only), confirm the amount, choose the Received in payment account (for example cash) and click Receive Rs ….

The Billing chapter (Chapter 34) explains that the invoice is issued at this moment: when payment is collected for charges that have no invoice yet, the Platform numbers and issues the invoice in the same transaction as the receipt. The result shows the receipt number and the invoice number, with Print receipt and Print invoice buttons. Exclusive tax, if configured, is added on top of the price. If the patient pays more than the charges, the extra money is held as advance. The same transaction records the doctor's commission entries (Chapter 35), which the doctor later sees under My earnings.

Status: [Implemented]. Module: Billing.

3.10 Cash close

At the end of the shift the cash is closed by someone who holds the cash-close permission. The default Receptionist role does not hold it; the Accountant and Admin roles do. In this story the Accountant opens Payments and clicks Close counter. The Platform shows the expected amount (payments minus refunds since the previous close). For a cash account the Accountant types the counted amount, adds a note if there is a difference, and clicks the close button. The close is an immutable record with a printable slip, and a difference above the alert amount shows a "Flagged" badge. Each close starts where the previous one ended, so no payment is counted twice. Closing never blocks taking payments (Billing, Chapter 34).

Status: [Implemented]. Module: Billing.

3.11 Closing the day

The doctor clicks Close day on My Queue. The button is disabled while a patient is still with the doctor. A dialog lists every patient still waiting, skipped or at a test, and for each one the doctor chooses to cancel them or transfer them to another doctor. When the list is settled the session closes and no more tokens are issued (Chapter 30). A session that is left open with patients still waiting is not cancelled automatically; the system logs an alert for an admin.

Status: [Implemented]. Module: Queue.

Chapter 5 — Request lifecycle: from a click to the database and back

This chapter follows one real request through the whole Platform: from a button in the web app, through the API's security checks, into a database transaction, and back to the screen. 5.1 The example: registering a patient

Status: [Implemented]

The traced request is the one a receptionist makes when registering a new patient. On the Patients page the receptionist clicks Create, fills the multi-step New Patient form and clicks Add Patient on the last step. The web app sends POST /patients, the API stores the patient and an audit record, and the web app shows the toast "Patient created" and offers to book a first appointment.

This request is a good example because it touches every common layer: the token and tenant headers, all five global guards, DTO validation, a permission check (patients.create), a database transaction with an audit row, the response envelope and the cache refresh in the web app. It does not use realtime events; section 5.8 covers those with a queue action instead.

Figure 5.1 — Sequence of one write request, POST /patients, from the receptionist's click to the toast.

The diagram has six participants from left to right: the Receptionist, the Web app, the apiClient axios instance, the API's guards and validation pipe, PatientsService, and PostgreSQL. (1) The receptionist fills the New Patient form and clicks Add Patient. (2) The web app calls createPatient, which first removes blank optional fields. (3) The axios instance sends POST /patients with the Bearer token and the x-organization-id and x-location-id headers. (4) JwtAuthGuard checks the access token. (5) TenantContextGuard checks in the database that the user owns the organization or has an active assignment at that location. (6) FeatureFlagGuard finds no @RequireFeature on this route and lets it pass. (7) AccessGuard resolves the user's access context and requires patients.create. (8) SubscriptionGuard checks that the clinic is not in read-only mode, because this is a write. (9) The ValidationPipe validates the body against CreatePatientDto. (10) The controller calls PatientsService.create with the tenant context, the DTO and the actor. On any error, for example 409 because the phone exists, the GlobalExceptionFilter returns the envelope with isSuccess: false and a message; the axios promise rejects and the web app shows the message in a toast.

5.2 In the browser: hook, service and the axios instance

Status: [Implemented]

In simple terms. The screen never talks to the server directly. It asks a small "mutation hook" to do the work; the hook calls a service function; the service function uses one shared HTTP client that adds the user's credentials and the clinic and branch the user is working in.

Technically.

  • The form component calls useCreatePatient().mutateAsync(data). This is a TanStack Query mutation whose mutationFn is createPatient from features/patients/services/patients.api.ts.
  • createPatient drops fields that are empty strings (the API would reject an empty dob or email) and calls api.post('/patients', body). It returns data.data, the payload inside the response envelope.
  • api is the axios instance apiClient in web-app/src/lib/api.ts:
    • Base URL: the VITE_API_BASE_URL build variable, default http://localhost:5000.
    • Timeout: 15 seconds. withCredentials: true, so the browser sends the refresh-token cookie.
  • Request interceptor. Before every request it reads the Zustand auth store (useAuthStore), which lives in memory only and is never written to browser storage:
    • adds Authorization: Bearer <access token> when a token exists;
    • for lab portal URLs (/lab-portal/...) adds only x-lab-id and no clinic headers;
    • otherwise adds x-organization-id (the active organization) and x-location-id (the active location).
  • Response interceptor. Described with the error path in section 5.7.

TanStack Query is configured once in web-app/src/lib/query-client.ts: queries are fresh for 5 minutes, are kept for 10 minutes, retry twice and do not refetch when the window regains focus; mutations retry once. Individual hooks may override these values (the access query, for example, uses 30 seconds and refetches on focus).

5.3 Arriving at the API: process start-up and Express middleware

Status: [Implemented]

An HTTP process is started by bootstrapHttp(role) in backend/src/bootstrap/http.ts (Chapter 6 explains the roles). It configures, in this order:

  1. The NestJS application with Nest's own body parser switched off.
  2. JSON and URL-encoded body parsers with a 5 MB limit (consent signatures are sent as inline images).
  3. The global ValidationPipe (section 5.5).
  4. The global exception filter GlobalExceptionFilter.
  5. CORS for one origin, CORS_ORIGIN (default http://localhost:3000), with credentials allowed.
  6. cookie-parser, so the refresh cookie can be read.
  7. A small middleware that opens a per-request context (RequestContextService, based on Node's AsyncLocalStorage).
  8. Listening on PORT (default 5000).

Two middleware classes exist in common/middleware/ (ContextMiddleware and TenantContextMiddleware) but no module registers them [Not implemented]. Tenant checks are done by a guard instead.

For every request NestJS then runs its fixed pipeline: Express middleware → global guards → interceptors (on the way in) → pipes → controller method → interceptors (on the way out) → exception filter if anything threw. The next sections walk this pipeline.

5.4 The five global guards

Status: [Implemented]

Five guards are registered as global guards (APP_GUARD) in backend/src/app.module.ts. NestJS runs them in registration order, and the first one that refuses stops the request.

# Guard Question it answers Skips when Refusal
1 JwtAuthGuard Is there a valid, unexpired access token? The method and path match an entry in PUBLIC_ROUTES (login, register, refresh, password reset, email verification, logout, the public theme, the TV display state, lab magic links). 401 with a message such as "Token has expired. Please refresh your token."
2 TenantContextGuard Does this user have access to the organization and location in the headers? @Public(); @ContextFree(); super admins. @RequireSuperAdmin() routes are checked here instead (non-super-admins get 403 "Super admin access required"). 400 "Missing tenant context. Please select an organization and location." or 403 "You do not have access to this organization/location".
3 FeatureFlagGuard Is every feature named by @RequireFeature active for this organization and location? No @RequireFeature on the route; @Public(); super admins. 403 'The "" feature is not enabled for this location'.
4 AccessGuard Does the user hold every permission in @Can(...), or is the user a member for @AnyMember()? @Public(); routes with neither marker pass (but still get the access context attached when an organization is known). 403 with { code: 'NO_PERMISSION', missing: [...] }.
5 SubscriptionGuard If this is a write, is the clinic out of read-only mode? Reads (GET, HEAD, OPTIONS); @Public(); super admins; paths starting /auth/, /account, /me/, /admin/subscriptions; requests with no organization. 402 with code: 'SUBSCRIPTION_EXPIRED'.

Details worth knowing:

  • Access check for the tenant. TenantContextGuard calls AuthorizationService.validateAccess. An owner passes for any active location of the organization. Anyone else needs an active assignment at that exact location with portal access switched on. When it passes, the guard stores request.tenantContext = { organizationId, locationId }.
  • @Public() and the JWT guard. JwtAuthGuard only reads the PUBLIC_ROUTES list (auth/constants/public-routes.ts). The @Public() decorator alone does not let an unauthenticated request through; a route without a token must also be listed there.
  • No path-prefix skips. TenantContextGuard deliberately has no list of path prefixes that bypass it; it relies only on the decorators.
  • Caching. The access context is cached per user, organization, location and access version (Chapter 11); the enabled-feature set for 30 seconds (Chapter 10); read-only status for 30 seconds per process.

5.5 Validation pipe and the controller

Status: [Implemented]

Validation. One global ValidationPipe validates every request body, query and parameter that is typed as a DTO class with class-validator rules. Its settings:

Setting Effect
transform: true The plain JSON body becomes an instance of the DTO class.
whitelist: true Properties without a validation decorator are removed.
forbidNonWhitelisted: true Instead of silently removing unknown properties, the request is refused with 400 (for example "property id should not exist").
enableImplicitConversion: true Query strings such as page=2 become numbers when the DTO says so.

The table lists the four options and their effect. The strict forbidNonWhitelisted rule matters for owners: a screen that sends a whole database row back (with id or timestamps) is refused, which is why some older edit screens fail (the Organizations and Locations chapter, Chapter 9, lists them).

Controller. In the example, PatientsController.create receives:

  • @Body() dto: CreatePatientDto — the validated body;
  • @ActiveTenant() ctx — { organizationId, locationId } from request.tenantContext (or the headers);
  • @RequestActor(ActorSide.CLINIC) actor — who is acting, for the audit trail.

Other handlers also take @Access() access, the resolved access context, when they need scope rules (Chapter 11). Controllers contain no business rules; they call a service and wrap the result.

5.6 Service, transaction and database

Status: [Implemented]

PatientsService.create shows the usual service pattern:

  1. Checks that read. The phone must be unique inside the organization (409 "A patient with this phone number already exists in this organization"). The next patient number is built from a count of the organization's patients, including deleted ones (P-00001, P-00002, …).
  2. One transaction for the write. dataSource.transaction(...) saves the patients row and writes the audit record through recordPatientChange with the same entity manager. Both rows commit together or not at all.
  3. A response DTO. The saved entity is mapped to PatientResponseDto.

Other modules follow the same shape with stronger guarantees where money or queues are involved: row locks (pessimistic_write), optimistic version checks, idempotency keys for queue actions, and outbox rows written in the same transaction (section 5.8). All tenant data is filtered by organization_id in the service; data that has a scoped permission is filtered further with applyScope (Chapter 11).

The database is PostgreSQL. The API connects with the DATABASE_URL connection string and always requests an SSL connection.

Success. Every controller returns ResponseWrapper.success(data, message). The JSON body is always the same envelope:

message A human-readable message, for example "Patient created successfully".
isSuccess true.
httpStatusCode Always 200 inside a success envelope, even when the HTTP status is 201.

The table describes the five fields of the envelope. The web app reads res.data.data for the payload. On the way out, the global VisibleIfInterceptor removes fields marked @VisibleIf that the caller may not see (for example treatment prices without patients.price.view); patient records have no such fields.

Back in the browser, the mutation's onSuccess invalidates every query whose key starts with patients, so open patient lists refetch, and shows the toast "Patient created". The modal then switches to an optional "Book First Appointment" step.

Errors. Any exception, anywhere after the middleware, reaches GlobalExceptionFilter. It logs the error and answers with the HTTP status of the exception (500 for unexpected errors) and an envelope with isSuccess: false, message (the first message when there are several, such as validation errors; "Something went wrong" for unexpected errors), error (the exception body, for example { code: 'NO_PERMISSION', missing: [...] }) and devMessage.

400 Validation failed, or tenant headers missing.
401 No token, invalid token or expired token.
402 SUBSCRIPTION_EXPIRED: the clinic is read-only.
403 No access to the organization or location, feature not active, NO_PERMISSION, or super admin required.

409 Business conflict, such as a duplicate phone number.

Automatic token refresh. The access token lives 15 minutes. When any request gets 401, the axios response interceptor:

  1. ignores 401s from /auth/login and /auth/refresh themselves;
  2. if a refresh is already running, parks the request in a queue;
  3. otherwise calls POST /auth/refresh (the httpOnly cookie carries the session id and refresh token), stores the new token and context in the auth store, replays the queued requests and retries the original request once;
  4. if the refresh fails, or the retried request gets 401 again, clears the auth store and sends the browser to /login.

5.8 The realtime path: from a commit to every open screen

Status: [Implemented]

In simple terms. When something changes in a doctor's queue, every screen showing that queue (the doctor screen, the reception board, the waiting-room TV) must update within moments, even when the Platform runs several API servers. The Platform does this with a "transactional outbox": the change and a "please announce this" note are saved together; a separate worker reads the notes and broadcasts them; every API server pushes them to the browsers that are listening.

Figure 5.2 — Sequence of a queue change travelling from the database transaction, through the outbox relay and Redis, to the web app.

The diagram has seven participants: the Receptionist, the API process, PostgreSQL, the OutboxRelayService (in the worker), Redis, the QueueGateway (the Socket.IO gateway in every API process) and the Web app. (1) The receptionist performs a queue action, for example a check-in. (2) The API begins a transaction, locks the queue session row and updates the queue entry. (3) In the same transaction it inserts a queue_events audit row and three outbox rows, and calls pg_notify('queue_outbox'). (4) It commits. (5) The receptionist gets the success response. (6) PostgreSQL delivers the queue_outbox notification to the relay (if the notification is missed, the relay also polls every second). (7) The relay selects up to 100 unpublished outbox rows with FOR UPDATE SKIP LOCKED. (8) It publishes each row to Redis on the realtime channel, and (9) Redis confirms. (10) The relay stamps published_at on those rows and commits. (11) Redis delivers the message to every API instance. (12) Each gateway emits queue.event to the session room and the location board room, and display.event to the location's display room. (13) The web app sees a newer sequence number and refetches the screen's snapshot over HTTP. A note across the relay and the gateway says that the worker sends a heartbeat every 5 seconds, and that an API instance that has heard no heartbeat for 15 seconds refuses socket connections, so clients fall back to polling.

Facts behind the figure:

  • Three outbox rows per change, one per room: session:<sessionId> (one doctor's queue), location:<locationId>:board (the reception board) and location:<locationId>:display (the TV). Payloads carry ids, statuses, tokens and a sequence number, never patient names.
  • At-least-once delivery. If Redis does not accept the batch, the relay's transaction rolls back and the rows are retried. Clients drop duplicates by sequence number.
  • Rooms and access. Clients connect to the /realtime Socket.IO namespace with their access token and subscribe to rooms. The gateway checks access per room: display rooms are open without login; session and board rooms need access to that location; org:<organizationId> needs access to the organization.
  • Access changes use the same sockets. When an organization's access version changes (a role edit, a feature switch), every process hears it over a separate Redis channel and the gateway emits access.changed to the org:<id> room. The web app then refetches GET /me/access (Chapter 11).
  • Single-process mode. In the all role (development), the relay hands rows straight to the local gateway and Redis is not needed for realtime.
  • Notifications use the same pattern with their own outbox table (notification_outbox) and relay loop (Chapter 6).

6.4 Who owns the database schema

Status: [Implemented]

In simple terms. The table structure is defined by the entity classes in the code. In development the API adjusts the database to the entities automatically on start. In production nothing changes the tables automatically: an operator first reviews the planned changes and then applies them. Hand-written migrations add what entities cannot express, such as triggers.

Technically.

  • Entities own table shapes. Only processes that serve HTTP own the schema (api and all); the worker never touches it.
  • Start-up order in a schema-owning process:
    1. ensurePostgresExtensions installs the btree_gist extension (needed by the doctor double-booking constraint) and a uuid_generate_v7() function (default primary key of the lab tables).
    2. The TypeORM connection starts. synchronize is on unless NODE_ENV is production.
    3. runPendingMigrations records the legacy baseline as applied, then runs pending migrations, each in its own transaction. If one fails, start-up fails.
  • Migrations. backend/src/migrations/ holds three files. 1776356529788-create-table.ts is a legacy baseline that is recorded as applied and never executed. The other two (doctor-compensation, lab-management-foundation) are hand-written and idempotent: they skip tables that already exist and add triggers and backfills.
  • Production. synchronize is off. The documented procedure is: build; review the SQL with npm run schema:log:prod; apply it with npm run schema:sync:prod after a backup; start one API instance so it runs the migrations; only then start further API instances and the worker (concurrent start-ups take no migration lock). Alternatively run npm run migration:run:prod as a release step.
  • CLI data source. The TypeORM command-line tools use backend/src/data-sourse.ts, which loads entities by file pattern. It therefore also sees entity files that no module registers (chairs and the old single inventory entity), which can show up in schema:log output.

Chapter 8 — The multi-tenant model

The Platform serves many clinic businesses from one installation and one database, and each business can have several branches. 8.1 Organizations, locations and the tenant boundary

Status: [Implemented]

In simple terms. An organization is one clinic business; it is the tenant. A location is one branch of that business. A dental group with three branches is one organization with three locations. Almost every record in the Platform (patients, appointments, invoices, staff assignments, queue sessions) carries the organization it belongs to, and most also carry a location.

Technically.

  • organizations is the tenant table. locations belongs to exactly one organization (organization_id, deleted with it by ON DELETE CASCADE). Each location has one location_settings row.
  • Tenant tables carry an organization_id column, and services always filter by the active organization. Data that differs per branch also carries location_id.
  • All tenants share one database and one schema. Isolation is done in application code (guards plus organization_id filters in every query), not by separate databases or database row-level security.
  • The super admin stands outside all tenants (users.global_role = 'super_admin') and can enter any active organization.

8.3 The employee person record and assignments

Status: [Partial] — the data model supports one person at several locations and clinics, but the API only ever creates one assignment per employee.

In simple terms. The Platform separates the person from the job. The employee record holds who the person is (name, phone, national ID number, gender, date of birth, photo). Each assignment says where and how that person works: in which organization, at which location, in which role, with which salary, and whether the person may sign in there.

Technically.

  • employees has no organization_id. Phone is unique across the whole Platform, and so is the national ID number when given.
  • employee_org_location_assignments holds, per job: organization_id, location_id, employment_role_id (the role, may be empty), designation, employee_code (unique per organization), an optional queue token_prefix, salary fields, has_portal_access, user_id (the staff login, may be empty), is_primary and is_active. One person can have at most one assignment per location (unique on employee_id, location_id).
  • Permissions are tied to the assignment, not to the person: the same person can be a Doctor at one location and have no role at another.
  • What the API does today. POST /employees creates the person and exactly one assignment, at the location the creator is working in. 8.5 The tenant context on every request

Status: [Implemented]

In simple terms. The web app always tells the API which clinic and which branch the user is working in. The API checks that the user is allowed there before doing anything else.

Technically.

  • The access token (a JWT, valid 15 minutes) carries only the user id, email, global role and session id. It does not carry the organization or location.
  • The web app's axios instance adds two headers to every request from the in-memory auth store: x-organization-id and x-location-id (lab portal requests carry x-lab-id instead).
  • TenantContextGuard, the second of the five global guards, reads the headers and calls validateAccess. Missing headers give 400 "Missing tenant context. Please select an organization and location."; no access gives 403. On success it stores request.tenantContext.
  • Controllers read the context with @ActiveTenant() and pass the organization id (and, where relevant, the location id) to the service, which filters every query by it.
  • The guard steps aside for @Public() and @ContextFree() routes and for super admins, and checks the super-admin role for @RequireSuperAdmin() routes. It has no path-prefix exceptions.
  • The organization and location in the headers also select the access context (Chapter 11) and the active features (Chapter 10).

8.7 Clinic time: the location's timezone

Status: [Implemented]

In simple terms. A clinic's day starts at midnight where the branch is, not where the server is. Each location stores its own timezone, and every "today", "now" and opening-hours check uses it.

Technically.

  • locations.timezone holds an IANA timezone name. New locations created through POST /locations default to UTC; the setup wizard copies the organization's timezone (default Asia/Karachi) to every location. The value is not validated; an unknown name falls back to UTC.
  • ClockService (common/clock/) is the single source of clinic time. timezoneFor(locationId) reads the timezone (cached for 60 seconds); today(tz) gives the local date; dayRange(tz, date) gives the UTC start and end of a local day; at(tz, date, time) converts a local wall-clock time; wallClock(tz, instant) gives the local weekday and time.
  • It is used by appointments (working hours, availability, same-day checks), the queue (the queue day and token day), billing, payroll, reports, notifications, employees and the lab modules.
  • Scheduled jobs are triggered by the server clock (Chapter 6); jobs that need a clinic day compute it through ClockService.

Technical references: backend/src/common/clock/clock.service.ts · ClockService · backend/src/common/clock/tz.util.ts

9.10 Owner's FAQ

Can an owner create a new organization? No. Only the super admin can, or a new owner through self-signup, which creates a separate clinic.

Can an owner add a branch? Yes, from Locations, as long as the plan's location limit allows it and the subscription has not expired.

Can a branch code be changed? No. The code is fixed at creation; the token prefix falls back to it.

Where is the sales tax rate set? In the location's settings (Tax Rate %) or in the setup wizard's location step. Each branch has its own rate.

What happens to patients and staff when a branch is deactivated? Nothing is deleted or moved. The branch is no longer offered at sign-in and in the location switcher.

What does "unmanaged" mean? An organization with neither trial end nor paid-until date. It never expires and has no plan limits. Organizations created by the super admin start this way.

Chapter 10 — Features: entitlement, enablement and location overrides

A feature is a named part of the Platform, such as "Invoices" or "Lab Management", that can be on for one clinic and off for another. This chapter explains the three switches that decide whether a feature is active (the super admin's entitlement, the owner's switch and a per-location override), the 24 features that exist, how the backend enforces them and which screens control them. It is written for the product owner, who sells and configures features per clinic.

10.1 The three switches

Status: [Implemented]

In simple terms. The platform operator decides what a clinic is allowed to have; the clinic owner decides what the clinic actually uses; and the owner can switch a feature off at one branch. A feature works at a branch only when all three agree.

Switch Who sets it Stored in Meaning
Entitled Super admin org_feature_flags.is_entitled, optional entitled_until The feature is part of this clinic's plan. With entitled_until, it is a trial that ends at that moment.
Enabled Owner (or anyone with admin.features.manage); the super admin can also set it org_feature_flags.is_enabled The clinic has switched the feature on. Only possible while entitled.
Location override Owner (same permission) location_feature_overrides.is_disabled Switches the feature off at one location. It can never switch on something the organization has off.

The table lists the three switches, who controls each, where it is stored and what it means. A feature is active for an organization when its catalog entry is active, it is entitled (and the trial has not ended), and it is enabled. It is active at a location when, in addition, that location has not switched it off.

Defaults and missing rows.

  • When an organization is created (by the super admin or by self-signup), the Platform writes one org_feature_flags row per active catalog feature: features that are "on by default" in the catalog are both entitled and enabled; all others are neither.
  • If an organization has no row for a feature, it counts as entitled, and enabled according to the catalog default. This keeps organizations that predate entitlement working.
  • A trial end date must be in the future when set. When it passes, the feature becomes "not entitled" with the reason trial_expired; the owner sees it locked.

10.3 How the backend enforces features

Status: [Implemented]

There are two mechanisms.

  1. Through permissions (the common case). Every permission names one feature. AccessResolver keeps a permission only if its feature is active at the request's organization and location (filterByFeatures). Turning a feature off therefore takes the permission away from every role without changing the roles; turning it back on restores access exactly as it was.
  2. Through @RequireFeature(key). Used where no permission expresses the feature, mainly on @AnyMember() routes. FeatureFlagGuard, the third global guard, collects every @RequireFeature key on the handler and its controller (both apply) and refuses with 403 'The "" feature is not enabled for this location' if any is not active. Super admins and @Public() routes skip the check. The location header narrows the set; the guard trusts it without a membership check, which is safe because a location can only remove features.

Caching. FeatureFlagsService keeps the active set per organization, and per organization and location, in process memory for 30 seconds. Every change clears the cache in the process that made it. The change also raises the organization's access version (automatically for org_feature_flags writes, explicitly for location overrides), which is broadcast over Redis so every other process drops its cache at once, and the web app gets access.changed and refetches. If Redis is down, other processes catch up within the 30-second lifetime.

Every change is audited in audit_logs (entity types org_feature_flag and location_feature_override), in the same transaction as the change, with the before and after values.

10.8 Owner's FAQ

What happens to roles when I turn a feature off? Nothing is deleted. The feature's permissions stop working for everyone; turning the feature back on restores them exactly.

Can I turn a feature on at one branch only? Not directly. Turn it on for the clinic and switch it off at the other branches.

Why can't I switch a feature on? It is not in your plan, or its trial has ended. Only the super admin can entitle it.

What happens when a trial ends? The feature becomes inactive at once (within the 30-second cache), and the owner's switch shows it locked with "trial ended".

Does turning a feature off log people out? No. Open screens receive an access update and lose the related menu items and buttons.

Chapter 11 — Roles and permissions

This chapter explains who may do what inside a clinic on the Platform. It covers the fixed list of 70 permissions, how they are grouped into roles, the five system roles every clinic starts with, how a clinic builds its own roles safely, and how the backend and the web app check permissions on every request and every screen. 11.1 The model in one paragraph

Status: [Implemented]

The Platform never checks role names. It checks permissions, such as billing.invoice.void. A role is a clinic-owned bundle of permissions, stored as a map { permission: scope or true } in employment_roles.permissions. An employee gets a role through an assignment at one location (Chapter 8), so the same person can have different roles at different branches. Owners and super admins have no role: they always get every permission at its widest scope. A permission whose feature is not active (Chapter 10) is dropped at resolution time. Anything not granted is denied (fail-closed).

11.6 Resolving access: AccessResolver, cache and access version

Status: [Implemented]

In simple terms. For each user, clinic and branch, the Platform works out once what the user may do, remembers the answer, and throws the answer away as soon as anything relevant changes.

Figure 11.3 — The access resolution path from a request to the permission checks in the backend and the web app.

The flowchart reads top to bottom. A request brings a user, an organization and a location. The resolver first reads the organization's access_version (cached for 15 seconds). It then asks whether a cached context exists for this user, organization, location and version that is less than 5 minutes old; if yes, it goes straight to the AccessContext. If not, it asks "Super admin or owner?". If yes, the user gets every permission at its widest scope. If no, it asks whether the user has an active assignment at this location with portal access and an active role. If no, the user gets no permissions; if yes, the role's grants are normalized and expanded with everything they imply. All three branches meet at "Drop permissions whose feature is not active here", which produces the AccessContext, offering can, scope, applyScope and decide. The context feeds two final boxes: the backend (@Can on handlers, applyScope on queries, @VisibleIf on fields) and the web app (GET /me/access, useAccess().can, the route gate, the sidebar and the buttons).

Technically.

  • AccessResolver.resolve(user, organization, location) builds an AccessContext holding: the user, organization, location, version, isSuperAdmin, isOwner, isMember (super admin, owner or portal-enabled assignment), the employee id, active features, granted permissions, the role and its home page.
  • The cache lives in process memory: at most 10,000 entries, 5 minutes each, keyed on user, organization, location and access version.
  • organizations.access_version is raised by one after any committed change to employment roles, assignments (role, location, organization, active flag, portal access, login), organization feature flags or ownership. An entity subscriber does this automatically for TypeORM writes, once per transaction after commit; location overrides and raw SQL bump it explicitly.
  • A bump is broadcast over Redis to every process, which drop their cached contexts and feature sets, and the Socket.IO gateway emits access.changed to the room org:<id>; open browser tabs refetch their access. If Redis is down, other processes catch up within 15 seconds (the version cache).
  • Fail-closed. A missing key is no access. Roles with only old-style boolean flags give nothing. A role that is inactive, or belongs to another organization, gives nothing. A location header that is not a valid id means no location, so staff get no role permissions.

11.9 Limitations and known gaps

  • A system role deleted directly in the database is recreated on the next start; a clinic cannot permanently remove a system role (the API refuses to delete one anyway).
  • Missing markers are caught by a unit test, not at runtime.
  • POST /auth/switch-location still returns eight old permission flags derived from the new permissions; the web app ignores them.
  • Permissions follow the assignment's location: a staff member with no assignment at the active location gets no role permissions there.

11.10 Owner's FAQ

Can a receptionist see treatment prices? Yes with the default Receptionist role, which holds patients.price.view. Without it, prices are removed from the API responses, not only hidden on screen.

Can I give my manager the right to edit roles without making them all-powerful? Yes: grant admin.roles.manage. They still cannot grant anything they do not hold themselves.

Why can't I edit the Doctor role? System roles are read-only templates. Clone it and edit the copy, then assign the copy.

How quickly does a role change take effect? On the next request: the change raises the access version, every server drops its cached answer, and open screens refetch their access.

What does a doctor see with patients.view at scope own? Only patients they have an appointment or queue entry with.

Where is the history of role changes? In the audit log, as employment_role entries with before and after values and the reason given for high-risk grants.
