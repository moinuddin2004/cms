Chapter 56 — Authentication and sessions

This chapter explains how a person proves who they are to the Platform and stays signed in: registering a clinic, signing in, choosing an organization and location, the short-lived access token and the long-lived session cookie, managing sessions, password flows, rate limiting and the staff-login administration screen. It is written for the product owner, who needs to know exactly how long a sign-in lasts, what a user can revoke and which protections exist today. What a signed-in person may then do is a different question, answered by Chapter 11 (roles and permissions) and Chapter 57 (access control in depth).

56.1 The model in one paragraph

Status: [Implemented]

A user is a login: an email address, a password hash and an account status (active, suspended or deleted). A user is not the same as an employee, who is the person record that the Employees module keeps (Chapter 37). A staff login links one user to one employee. Signing in creates a session row in the database and gives the browser two things. The first is an access token, valid for 15 minutes, which the web app keeps in memory only and sends as a Bearer header. The second is a session cookie named refresh_token, which is httpOnly (scripts cannot read it) and carries the session id and a long random secret. When the access token expires, the web app calls POST /auth/refresh; the cookie proves the session is still valid and a new access token is issued. Nothing about the login is stored in the browser's local storage.

56.3 Features

56.3.1 Register a clinic (self-signup)

Status: [Implemented]

What it does. Lets a new clinic owner create the login and the clinic in one step. The Platform creates the user, a new organization with a main location and a 14-day trial (Chapter 45 covers subscriptions and onboarding), sends a verification email and signs the owner straight in.

How the user does it.

  1. Open the sign-up page and enter clinic name, name, email, optional phone and a password.
  2. Submit. The owner lands in the application, kept signed in for 30 days.
  3. Later, click the link in the verification email.

Behind the scenes — technically. POST /auth/register is public and rate limited. AuthService.register creates the user, calls the clinic set-up service to create the organization, and sends the verification email. If clinic creation fails, the new user row is deleted so no empty login remains. It then runs the normal login flow with "keep me signed in" on.

Rules and validations.

  • Email must be a valid address; name and clinic name are required (at most 255 characters); phone at most 20 characters; password at least 6 characters.
  • An email that already exists is refused.
  • The verification email failing to send is logged but does not stop registration.

Who can do it. Anyone; the route is public.

Data read and written. users, organizations, locations, owner link, subscription rows, user_sessions, security_logs.

Error cases. 429 when more than 5 sign-ups come from one address in an hour; 400 for invalid fields or a duplicate email.

Technical references: backend/src/auth/auth.controller.ts · register · backend/src/subscriptions/clinic-setup.service.ts · web-app/src/features/auth/components/RegisterForm.tsx

56.3.2 Verify an email address

Status: [Implemented]

What it does. Confirms that the owner controls the email address. Verification is informational: an unverified user can still sign in and work. The web app shows a "verify your email" banner until verification is done.

How the user does it. Click the link in the email, which opens /verify-email?token=…. The page shows "Verifying your email…" and then a success or failure message. A signed-in user whose address is still unverified can ask for a fresh link.

Behind the scenes — technically. The email carries a random 32-byte token; the database stores only its SHA-256 hash, valid for 48 hours. POST /auth/verify-email (public, 10 attempts per 15 minutes) hashes the supplied token, finds an unexpired match and sets email_verified_at. POST /auth/resend-verification (signed in, 3 per hour) issues a new token; if the user has no pending token it answers "Email already verified". Sending depends on SMTP settings in the server environment (SMTP_USER, SMTP_PASS).

Rules and validations. An invalid or expired token gives 400 "This verification link is invalid or has expired". Users created by an administrator through user administration are not sent a verification email.

Who can do it. Anyone holding the token; resend needs a signed-in user.

Data read and written. users (email_verification_token, email_verification_expires, email_verified_at).

Technical references: AuthService.verifyEmail · AuthService.resendVerification · backend/src/common/services/mail.service.ts · web-app/src/features/account/pages/VerifyEmailPage.tsx

56.3.3 Sign in

Status: [Implemented]

What it does. Checks the email and password, creates a session and returns the information the web app needs to continue: the user, an access token, the organizations and locations the user may enter, and flags saying whether an organization or location still has to be chosen.

How the user does it. Enter email and password, optionally tick "Keep me signed in for 30 days", and click sign in.

Behind the scenes — in simple terms. The server looks up the user, compares the password against the stored hash, refuses suspended or deleted accounts, records a new session, and works out where the person is allowed to go. The session lasts one day, or 30 days if the box was ticked. Only five sessions can be active at once; a sixth sign-in quietly revokes the oldest.

Behind the scenes — technically. POST /auth/login (public; 5 attempts per 15 minutes per address and route). UserService.validateUser compares with bcrypt (12 rounds). SessionService.createSession stores a bcrypt hash of a 64-byte random refresh secret, the user agent, parsed browser, operating system and device, and the client IP. AuthorizationService.resolveUserAccess returns the accessible organizations. The response also lists any lab memberships, so a user who works only for a lab is sent to the lab portal (Chapter 41). The cookie is httpOnly, sameSite=lax, secure in production, with a maximum age equal to the session's remaining lifetime.

Rules and validations.

  • Email valid; password at least 6 characters.
  • A wrong email or password gives a plain 401 with no hint about which was wrong.
  • A suspended account gets 403 "Your account has been suspended. Please contact support."; a deleted account gets 403 "This account has been deleted."
  • A session's expiry is fixed at sign-in and is never extended by refreshing.

Who can do it. Anyone with an account.

Data read and written. users, user_sessions, employee_org_location_assignments, owner links, organizations, locations, security_logs (a success row).

Effects on other modules. The login result seeds the web app's auth store, which every later request reads for its tenant headers (Chapter 8).

Error cases. 401 wrong credentials; 403 suspended or deleted; 429 too many attempts (message "Too many requests. Please try again later.", with a retryAfter value in seconds).

Technical references: AuthService.login · SessionService.createSession · AuthorizationService.resolveUserAccess · web-app/src/features/auth/components/LoginForm.tsx

56.3.4 Choose and switch organization and location

Status: [Implemented]

What it does. Decides which clinic and branch a person is working in. Every later request carries that choice in two headers.

How the user does it. After sign-in the selector appears when a choice is needed. Later, the location switcher in the page header changes the active location.

Behind the scenes — in simple terms. A single organization with a single location is chosen automatically. A super admin always picks an organization first. Otherwise the person picks, and the Platform remembers the last choice for next time.

Behind the scenes — technically. The login response sets requiresOrgSelection and requiresLocationSelection. POST /auth/select-location and POST /auth/switch-location (both signed in, context free) validate access with AuthorizationService.validateAccess and save last_accessed_organization_id and last_accessed_location_id on the user. Switching also returns the legacy permission flags for the new location (deprecated; the web app reads GET /me/access). Chapter 8 describes the choice flow and what each type of user may enter in full.

56.3.5 Stay signed in: access token, refresh cookie and silent refresh

Status: [Implemented]

What it does. Keeps a person signed in across page reloads and across the 15-minute life of the access token, without storing credentials in the browser.

Behind the scenes — in simple terms. The access token is a short pass kept only in the page's memory. When the page is reloaded the memory is empty, so the web app quietly asks the server for a new pass using the cookie. When a pass expires in the middle of work, the same quiet request happens and the failed request is repeated.

Behind the scenes — technically.

  • The access token is a JWT signed with the server's access secret, expiring in 15 minutes, holding the user id, email, global role and session id. There is no JWT refresh token; the refresh secret is a random value whose bcrypt hash lives on the session row.
  • On every app start the root route calls POST /auth/refresh once ("silent refresh"). On success the auth store is filled; on failure the user is treated as signed out.
  • POST /auth/refresh (public) reads the cookie, validates the session (not revoked, not expired, secret matches), re-checks the account status, rotates the refresh secret (the old one stops working) and returns a new access token and the full login payload. The cookie's expiry is the original session expiry, not a fresh window.
  • When any API call returns 401, the axios interceptor refreshes and retries once (Chapter 61 shows the sequence).
  • The auth store is memory only; it never uses local storage.

Rules and validations. A missing, revoked or expired session gives 403 "Invalid or expired session" and the cookie is cleared. A session whose user turned suspended or deleted is revoked on the spot.

Who can do it. Any browser holding a valid cookie.

Data read and written. user_sessions (refresh_token_hash, last_active_at).

Technical references: AuthService.refreshTokens · SessionService.rotateRefreshToken · JwtTokenService · backend/src/session/session-lifetime.ts · web-app/src/lib/api.ts

56.3.6 Sign out, list and revoke sessions

Status: [Implemented]

Figure 56.6 — Status lifecycle of a session.

The diagram shows a session starting at a dot and entering active when the user logs in or registers. A loop on active is labelled refresh: a refresh rotates the secret but keeps the same session and the same expiry. Active moves to revoked in three ways: the user logs out or revokes a session (single, all others or all), the user changes or resets the password, or the user is deleted. Active moves to expired when expires_at passes, which is one day or 30 days after sign-in. Revoked and expired are both final states. (A sixth sign-in also revokes the oldest session; the diagram leaves that case out to stay readable.)

What it does. Lets a user end the current session, see every active session with device details, and end any of them.

How the user does it. Open Settings, Sessions (or /sessions). Click Revoke on a row, Sign out on the current row, or Sign out all others. The toasts are "Session revoked", "Signed out successfully" and "All other sessions revoked".

Behind the scenes — technically.

Action Endpoint Notes
Sign out this session POST /auth/logout Public; reads the cookie, revokes that session, clears the cookie, writes a security log row
List active sessions GET /auth/sessions Newest activity first; marks the current one
Revoke one session DELETE /auth/sessions/:id Only the caller's own sessions; otherwise 404
Revoke all others POST /auth/sessions/revoke-all Keeps the current session

Rules and validations. A revoked session cannot refresh. An access token that was already issued stays valid until it expires, at most 15 minutes, because requests are checked by the token only.

Who can do it. Any signed-in user, on their own sessions.

Data read and written. user_sessions, security_logs.

Error cases. 404 "Session not found" for an id that is not the caller's.

56.3.7 Passwords: change, forgot and reset

Status: [Implemented] for change, forgot and reset. Add password is [Partial]: the endpoint exists but no screen calls it, because it is meant for accounts created through the disabled OAuth sign-in.

What it does. Lets a user change a known password, or recover from a forgotten one through an emailed link.

How the user does it.

  • Change: Settings, Security, enter the current and new password. All other sessions are revoked, as the page says.
  • Forgot: on the login page click "Forgot password?", enter the email and click "Send reset link". The page always says to check the inbox.
  • Reset: open the link in the email, enter a new password.

Behind the scenes — technically.

  • POST /auth/change-password (signed in) checks the current password with bcrypt, hashes the new one (12 rounds), and by default revokes every other session, keeping the current one.
  • POST /auth/forgot-password (public, 3 per hour) always answers "If the email exists, a reset link will be sent", whether or not the address exists. For a real user it stores the SHA-256 hash of a random token, valid for 15 minutes, and emails the link.
  • PATCH /auth/reset-password (public) hashes the supplied token, finds an unexpired match, sets the new password, clears the token and revokes all sessions of that user.
  • POST /auth/add-password (signed in) sets a password only when the account has none; otherwise 400 "Account already has a password".
  • All three paths write security log rows (change, reset requested, reset succeeded).

Rules and validations. Password rules are in section 56.5. A wrong current password gives 401 "Current password is incorrect". An invalid or expired reset token gives 400 "Invalid or expired token". Reset has no rate limit of its own; the token is single use and short lived.

Who can do it. Anyone for forgot and reset; signed-in users for change.

Data read and written. users (password, password_reset_token, password_reset_expires), user_sessions, security_logs.

Technical references: AuthService.changePassword · AuthService.forgotPassword · AuthService.resetPassword · AuthService.addPassword · web-app/src/features/auth/components/ForgotPasswordForm.tsx · ResetPasswordForm.tsx · web-app/src/features/settings/pages/SettingsPage.tsx

56.3.8 Rate limiting

Status: [Implemented], with a limit: the counters live in the memory of one API process.

What it does. Slows down guessing and abuse on the public and sensitive authentication routes.

Behind the scenes — technically. RateLimiterGuard counts requests per client address and route in a fixed window and answers 429 with retryAfter when the count is exceeded. The address comes from the first value of the forwarding header when present, otherwise the connection address.

Endpoint Allowed Window
POST /auth/login 5 15 minutes
POST /auth/register 5 1 hour
POST /auth/verify-email 10 15 minutes
POST /auth/resend-verification 3 1 hour
POST /auth/forgot-password 3 1 hour

The table lists the five throttled endpoints with their allowed attempts per window. Other routes, including refresh, reset-password and all clinical routes, have no limiter. A separate small throttle (120 requests per minute per address by default) protects the public lab magic-link routes (Chapter 41). Because the counters are in process memory, they reset when the process restarts and are not shared between API processes, so with several API processes the effective limit is higher. The code notes that a shared store such as Redis would fix this.

Who can do it. Not applicable; it applies to everyone.

Technical references: backend/src/auth/guards/rate-limiter.guard.ts · RateLimiterGuard · RateLimit · backend/src/lab-access/magic-links/magic-link-throttle.guard.ts

Status: [Partial]

Successful sign-in, sign-out, sign-out everywhere, password change, password reset requested, password reset succeeded, and a failed sign-in only for suspended or deleted accounts. 56.3.10 User administration and staff logins

Status: [Implemented]

What it does. Lets a super admin, an owner, or a user with the permission admin.users.manage create, edit, suspend and delete logins. The most common case is giving an existing employee a login.

How the user does it.

  1. Open User Admin (/users) and click Create User.
  2. Choose the type. For Staff, pick the employee from the list of staff who have no login yet.
  3. Enter name, email and a password of at least 8 characters, and save.

Behind the scenes — technically.

Action Endpoint
Profile of the caller GET /user/me
List users by type (super_admin, owner, employee), paged GET /user
Staff without a login GET /user/staff-candidates
Create a user POST /user
Edit a user (including status and password) PATCH /user/:id
Delete a user DELETE /user/:id

The table lists the user endpoints. The controller is context free and checks access itself: a super admin may act with or without an organization; anyone else must send an organization header and hold admin.users.manage at their location.

A staff login (type employee) runs in one transaction that locks the employee's active assignments in the organization. It refuses an employee who already has a login (409 "This employee already has a login") and an email already in use. It creates the user, then links the user to all of the employee's active assignments and switches portal access on for them. The login grants no permission by itself: what the person can do comes from the role of each assignment (Chapter 11). Changing assignments bumps the organization's access version, so the change reaches open tabs (Chapter 57).

Rules and validations.

  • Only a super admin can create or edit a super admin. Only an owner can add, edit or delete another owner.
  • A non-super-admin manager may touch only users of their own organization, never a super admin, and cannot elevate a user to super admin.
  • Creating a user checks the plan's login limit for the organization (error code PLAN_LIMIT); super admins may exceed it.
  • Delete is a soft delete: the status becomes deleted, a deletion time is set and every session of the user is revoked.
  • Passwords created here need 8 characters, which is stricter than the 6 required elsewhere.

Who can do it. Super admin, owner, or admin.users.manage (high-risk; the Admin system role holds it).

Data read and written. users, organization_ownership, employee_org_location_assignments.

Error cases. 403 for the manager-scope rules in this list; 409 existing login; 400 duplicate email.

56.4 Entities

The tables involved are users, user_sessions, security_logs and the unused oauth_providers; Chapter 13 describes them column by column. 56.6 Limitations and known gaps

  • Revoking a session does not cancel an access token that was already issued; it works until it expires, at most 15 minutes.
  • Rate-limit counters are per process and lost on restart.
  • The security log has no reader and no clean-up; failed password attempts are not recorded.
  • No two-factor authentication, no password strength enforcement and no lockout of an account after repeated failures.
  • Session rows are never deleted, only flagged.

56.7 Owner's FAQ

How long does a sign-in last? One day by default and 30 days when "Keep me signed in for 30 days" is ticked. The length is fixed at sign-in; using the application does not extend it.

If an employee leaves, how do I cut off access at once? Set the user's status to suspended or delete the user in User Admin. Deleting revokes every session; a suspended user is refused at the next refresh. An access token already issued may still work for up to 15 minutes.

Can one person have several logins on different devices? Yes, up to five active sessions. A sixth sign-in revokes the oldest.

What happens if someone forgets their password? They use "Forgot password?". The link lasts 15 minutes and a successful reset signs the user out of every device.

Can staff sign in with Google? No. That feature is built but disabled.

Where do I see failed sign-in attempts? Nowhere in the application today. Only the throttle protects the login route.

Chapter 57 — Access control in depth

This chapter follows the Platform's access control from the first guard that sees a request to the last button hidden in the browser. It is written for the product owner, who needs to know where a permission is checked, how quickly a change reaches users and which protections do not exist. Chapter 11 explains the permission catalog, the system roles and the roles screen; this chapter does not repeat them and goes deeper into the mechanics. Customization screens (features, roles, sidebar, theme) are in Chapter 58.

57.1 The idea in one minute

Status: [Implemented]

Access control answers four separate questions, in this order: Is this a real, signed-in user? Is this user allowed to work in this organization and location? Is the feature switched on for this clinic? Does the user's role hold the permission this action needs? A fifth check asks whether the clinic's subscription still allows writing. Each question is a global guard that runs before the controller. After the guards, two more mechanisms narrow what a person sees inside a permitted action: row scope (only own, location or organization rows) and field hiding (prices removed from a response). The browser repeats the same questions only to decide what to show; the server never trusts the browser.

Technical references: backend/src/app.module.ts · backend/src/access/ · web-app/src/features/access/

57.2 The five guards in order

Status: [Implemented]

Five global guards run on every HTTP request, in a fixed order, and the first refusal stops the request (Chapter 5, section 5.4, lists them with their skip rules).

Figure 57.1 — The five global guards in the order they run, with the refusal each can give.

The flowchart reads from top to bottom. A Request enters guard 1, JwtAuthGuard, which asks whether the token is valid; if not, the answer is 401 and the request is refused. Guard 2, TenantContextGuard, asks whether the organization and location in the headers are allowed for this user; if not, the answer is 400 (headers missing) or 403. Guard 3, FeatureFlagGuard, asks whether the required feature is active; if not, 403. Guard 4, AccessGuard, asks whether the permission is held; if not, 403 with the code NO_PERMISSION. Guard 5, SubscriptionGuard, asks whether a write is allowed; if the subscription has expired the answer is 402. A request that passes all five reaches the handler, where row scope and field hiding apply. Every refusal leads to the same "Refused" box.

The details that matter to an owner:

  • Guard 1 and public routes. JwtAuthGuard skips only the routes in a fixed public list (sign-in, register, refresh, password routes, email verification, logout, the public theme, the waiting-room display state and the lab magic links). Marking a handler @Public() is not enough on its own; the route must also be in that list.
  • Guard 2 and super admins. A super admin passes without headers. @RequireSuperAdmin() routes are checked here: anyone else gets 403 "Super admin access required". @ContextFree() routes skip the tenant check, and the handler then checks access itself. The guard has no path-prefix exceptions. A user passes for an organization if they own it, or if they have an active assignment at that exact location with portal access on.
  • Guard 3 only runs for tagged routes. @RequireFeature('key') is needed only on routes that use @AnyMember(), because a permission already implies its feature (the access context drops permissions of inactive features).
  • Guard 4 attaches the access context. Whenever the request names an organization, it puts the resolved access context on the request for the handler, even on routes with no permission marker.
  • Guard 5 is read-only mode. It refuses writes with 402 SUBSCRIPTION_EXPIRED for a clinic whose subscription has lapsed. Reads, super admins and the paths for signing in, the account, /me/ and subscription administration stay open.

57.4 The access context

Status: [Implemented]

For each request that names an organization, AccessResolver builds an AccessContext: user id, organization, location, access version, super-admin flag, owner flag, member flag, employee id, active features, granted permissions (feature-filtered, with implied permissions expanded), the role and its home page. Owners and super admins receive every permission at its widest scope. Staff receive the permissions of the role on their assignment at the active location, and only if portal access is on for that assignment. A role that is inactive or belongs to another organization gives nothing. A missing key means no access.

The context offers a small set of questions that code uses instead of role names:

  • can(permission) and canAll([...]): is it granted.
  • scope(permission): own, location or org, or nothing. An unscoped grant reads as org.
  • applyScope(queryBuilder, permission, columns): adds the row filter to a database query. With own it adds a condition on the caller's employee id (or a custom condition). With location it adds a condition on the active location. With org it adds nothing, because the organization filter is the caller's. With no grant, or when the caller has no employee record or no location to match, it adds a condition that matches no rows. If a developer forgets to name the column, it throws an error rather than silently showing nothing.
  • decide(permission, { value, min, max, approvalFlow }): returns allow, deny or "needs approval". Inside the range the answer is allow; outside it, allow only when the caller holds the escalation permission (today: preset discounts are escalated by the custom-discount permission), otherwise needs approval when the clinic runs an approval flow, else deny.

Field hiding. A response class can mark a property @VisibleIf('patients.price.view'). A global interceptor removes that property from every instance in the response when the caller lacks the permission, and removes every guarded field when there is no access context. It works only on class instances, not on plain object literals.

57.7 How fast a change reaches users

Status: [Implemented]

Each organization has a counter, organizations.access_version. It is raised by one after any committed change that can alter someone's access: employment roles (any column), assignments (role, location, organization, active flag, portal access or linked login), organization feature flags, ownership, location feature overrides and sidebar layout changes. An entity subscriber does this automatically for writes made through the data layer, once per transaction after the commit and never on rollback. Code that uses raw SQL or database cascades must bump explicitly; the employee delete path does.

Figure 57.3 — Sequence from an owner's role change to the refreshed browser tabs.

The diagram has six participants: the Owner, the API process, PostgreSQL, the AccessChangeBus, the QueueGateway and a Staff browser tab. (1) The owner saves a role change. (2) The API commits the role row. (3) The API increments access_version of the organization. (4) The API publishes the organization id and new version to the bus. (5) The bus drops cached access contexts of that organization. (6) It notifies listeners in this process and, through Redis, in the other processes. (7) The gateway emits access.changed to the organization's room. (8) The browser tab calls GET /me/access. (9) The API answers with new permissions and features. (10) The sidebar and buttons update and the route gate checks again.

The timing rules are:

  • Version cache. Each process caches the current version of an organization for 15 seconds. The bus updates it at once in every process that hears the change.
  • Context cache. Access contexts are cached in process memory, at most 10,000, for at most 5 minutes, keyed by user, organization, location and version. A new version means a new key, so stale entries are never used.
  • Redis. One Redis channel carries access-change messages between API and worker processes. If Redis is down, only the process that made the change learns at once; the others catch up within 15 seconds, when their cached version expires.
  • Feature cache. The enabled-feature set is cached for a short time and dropped by the same bus.
  • Browser. Open tabs refetch when told, on focus, and in any case after 30 seconds of staleness.

In practice, an owner's change reaches other staff within seconds, and within 15 seconds even when Redis is unavailable. A person who is already inside a permitted request is not interrupted.

57.9 Row-level security does not exist

Status: [Not implemented]

The database has no row-level security policies. 57.10 Limitations and known gaps

  • Tenant isolation is application-level only (section 57.9).
  • A handler without a marker passes the access guard at runtime; only the coverage test prevents it.
  • Contexts and version numbers are cached in process memory; with Redis down, other processes may lag up to 15 seconds.
  • An access token already issued is not re-checked against the session; permissions, however, are checked on every request from the access context, so a role change takes effect without a new token.
  • The ownerOrSuperAdmin sidebar flag is unused today.

57.11 Owner's FAQ

I removed a permission from a role. When does it stop working? Within seconds for open screens (the browser is told over the realtime connection) and on the next request on the server. At worst 15 seconds if the message bus is down.

A user opens a page by typing its address. Can they bypass the sidebar? No. The route gate shows No access and the API refuses the data calls with 403 NO_PERMISSION. Hiding a sidebar item is cosmetic; the checks are the permission on the route and on the API.

Does the sidebar layout give anyone access? Never. The layout only arranges pages the registry knows; every item still needs the viewer's permission.

Can the database stop one clinic seeing another's data? Not by itself. The application filters every query by organization; there are no database row-level policies.

Who can see which patients? The scope of patients.view: a doctor sees own patients, front desk sees the location, an admin sees the organization (Chapter 11).

What does 402 mean? The clinic's subscription expired; the clinic is read-only until a payment is recorded (Chapter 45).

Chapter 59 — Notification mechanics

This chapter explains how a notification travels inside the Platform, from the business event that causes it to the bell icon where a staff member reads it. It is written for the product owner who wants to understand the pipeline and its guarantees. The Notifications module chapter (Chapter 44) describes the settings screen, the event catalog and what users see; this chapter covers only the mechanics. Today the Platform delivers notifications in the application only: WhatsApp, SMS and email are prepared in the code but have no real sender.

59.1 The pipeline

Status: [Implemented] for in-app delivery. [Not implemented] for WhatsApp, SMS and email.

A notification event is a named thing that happens, such as order.submitted or item.ready (21 are seeded, all about lab orders, shipments, stages, appointments linked to labs and payments). When a workflow step runs the notify effect, the Platform decides who should be told, whether each person wants it, what the message says and when it may be sent. The result is one row per person and channel in a table called notification_outbox. A separate loop in the worker process sends those rows later. This is the transactional outbox pattern: the notification row is written in the same database transaction as the business change, so it exists only if the change was committed.

59.2 Event, recipients and audiences

Status: [Implemented]

The notify effect names an event code (and may narrow the audiences). An unknown code fails the whole transition, so a typo can never silently drop messages. Who receives the message is decided by a recipient resolver registered per kind of subject: the module that owns the subject says how to find its doctor, coordinator, lab and patient. Today only the lab order workflow registers one, so lab events are the only ones that produce notifications.

There are four audiences: patient (the only external audience), doctor, coordinator and lab. A recipient is a user (a signed-in person), a patient or a lab contact. The same person listed twice, or under two audiences, gets one row per channel. If an event is not meant for an audience, enqueueing for it fails with NOTIFICATION_AUDIENCE_INVALID. A patient is looked up in the same organization, so a clinic can never message another clinic's patient.

59.3 Rules and the decision order

Status: [Implemented]

For every recipient and channel the Platform makes one decision. The first check that matches wins:

  1. An internal audience with a mandatory event on the in-app channel is queued, ignoring settings.
  2. If the audience's master switch is off, the row is stored as skipped_disabled.
  3. If the rule for this event and channel is off, it is skipped_disabled.
  4. If the patient opted out of the channel, it is skipped_opt_out.
  5. If the time is inside the audience's quiet hours (and the channel is not in-app), it is held_quiet_hours until the window ends.
  6. Otherwise it is queued for now.

Skipped rows are still written, so the clinic can see in its message log why nothing was sent. Defaults apply when a clinic has set nothing: the patient audience and every patient rule are off; internal audiences are on, with in-app on and the external channels off. The channels offered per audience in code are in-app only for doctor, coordinator and lab, and none for patients, so patients receive nothing today.

Quiet hours are a start and end time per audience. The window can cross midnight (for example 22:00 to 08:00); equal start and end means no window. They use the audience setting's timezone if it names one, otherwise the timezone of the location the event belongs to (Chapter 62), otherwise UTC. In-app messages are never held, because they are silent.

59.5 Outbox, relay and sending

Status: [Implemented]

Figure 59.2 — Status lifecycle of a row in notification_outbox.

The diagram starts at a dot and shows several entry points. A row is created as queued when the decision allows sending, as held_quiet_hours when it falls inside quiet hours, as skipped_disabled when a switch or rule is off, as skipped_opt_out when the patient opted out, and directly as failed when the channel needs an address and the recipient has none. A held row becomes queued when the relay claims it once the quiet window has ended. A queued row becomes sent when the provider accepts it. A queued row whose send fails stays queued and is tried again after a pause. It becomes failed on a permanent error or at the fifth attempt. sent, failed and both skipped statuses are final. The status delivered exists in the code for providers that report delivery but nothing sets it today.

The relay (NotificationRelayService) runs only in processes that run jobs, which is the worker. It is woken at once by a database NOTIFY sent inside the enqueue transaction (so it fires only on commit) and also polls every two seconds, which picks up retries and quiet-hours rows that are due. If the NOTIFY connection fails, it logs a warning and relies on polling.

Sending works like this:

  • A row is claimed with one short statement that locks it so no other worker takes it, adds one to its attempt count and pushes its due time out by a five-minute lease. If a worker dies mid-send, the row reappears after the lease.
  • The provider is called with no transaction open; the result is written back only if this claim is still the latest.
  • A failure is retried after 30 seconds, 2 minutes, 10 minutes and one hour; the fifth failure makes the row failed. A provider can mark an error permanent to skip retries.
  • Delivery is at least once. The in-app copy is protected by a unique link to the outbox row, so a retry after a crash never shows the same message twice.
  • Batches of 50 are processed until nothing is due.

Providers. The in-app provider writes user_notifications (user, event, title, body, link, read time). The development provider logs WhatsApp, SMS and email messages and marks them sent, so flows run end to end; it sends nothing to anyone. A real provider can take over a channel through the provider registry.

Chapter 61 — Error handling

This chapter describes how the Platform reports problems: the shape of every API answer, the families of error codes, how validation and database conflicts become messages, how retries stay safe, and what the web app shows the user. It is written for the product owner and for support staff who read an error message and need to know what it means. Chapter 5 traces one request through the system and shows the main status codes; this chapter goes into the error side in more detail.

61.1 The envelope

Status: [Implemented]

Every controller answers inside one JSON envelope built by ResponseWrapper. On success the fields are data (the payload), message (for example "Patient created successfully"), isSuccess (true) and httpStatusCode (always 200 in the envelope, even when the HTTP status is 201). On failure the global exception filter GlobalExceptionFilter builds the same envelope with isSuccess false, the real HTTP status in httpStatusCode, a short message for people, a devMessage with a technical text for developers and an error field holding the exception body. The web app reads res.data.data on success and err.response.data.message (or error.code) on failure.

61.2 What the filter does with an error

Status: [Implemented]

Figure 61.1 — How an exception becomes an envelope and a message on screen.

The flowchart reads from top to bottom. An "Exception anywhere" in the request reaches GlobalExceptionFilter. The filter asks whether it is an HTTP exception. If yes, the request keeps its own status and body, with a code, a message and any extra fields. If no, which means an unexpected failure, the answer is 500 with the message "Something went wrong". Both branches build the envelope: isSuccess false, message, devMessage and error. The web app then shows a toast, an ErrorState panel or a friendly text chosen by the error code.

Categories of error:

  • Expected HTTP errors. Business rules and security refusals are thrown as typed exceptions with a status and, in most modules, a machine-readable code. The message is written for the user.
  • Validation errors. The global validation pipe rejects bad input (section 61.3). Several messages are possible; the envelope's message shows the first one.
  • Unexpected errors. Anything that is not an HTTP exception, such as an unhandled database failure, is logged with its stack on the server and answered as 500 "Something went wrong". The user-facing text never contains internals.
  • Rate limit. A throttled request is answered 429 with "Too many requests. Please try again later." and a number of seconds to wait (Chapter 56).

Every error is logged by the application logger together with the request address.

61.3 Validation

Status: [Implemented]

The global validation pipe converts input to the types named in each request class and has whitelist and forbidNonWhitelisted on. A request that contains a field the API does not define is rejected with 400, not silently ignored, and a field with a wrong type or format is rejected with a message such as "email must be an email". Request classes use validation decorators for lengths, formats, enumerations and nested objects. The same rules appear in the web app as form schemas, so most mistakes are caught before the request leaves the browser; the server rule is the one that counts.

61.5 Safe retries: idempotency keys and If-Match

Status: [Implemented]

Two mechanisms protect against double clicks, flaky networks and two people editing the same record.

Idempotency-Key. A client sends a header Idempotency-Key (1 to 150 characters) on actions that must not run twice. The server stores the key, a hash of the request and, once finished, the response, inside the same transaction as the work. If the same key arrives again with the same request, the stored answer is replayed and nothing runs twice. The same key with a different request gives 422 IDEMPOTENCY_KEY_REUSED. The same key while the first request is still running gives 409 REQUEST_IN_FLIGHT. A missing key where one is required gives 400 IDEMPOTENCY_KEY_REQUIRED. The key is required on every queue change, on patient check-in from an appointment, on money-moving lab billing posts and on the workflow engine transitions; the web app creates a fresh key for each open sheet or action. Queue idempotency keys are deleted after 24 hours by a nightly job.

If-Match and versions. Records that two people may edit carry a version number. A client may send If-Match: <version> (queue entries, lab order actions) or the version in the body; the server checks it while holding a row lock and, if the record has moved on, answers 409 with VERSION_CONFLICT or STALE_VERSION and the current state or version. The web app reloads and asks the user to try again, with texts such as "Someone else changed this just now. The latest version is loaded".

61.6 Database constraints become messages

Status: [Partial]

Chapter 62 — Time, money and document numbers

This chapter explains three rules that run through every module: how the Platform decides what time it is for a clinic, how it stores and calculates money, and how it numbers invoices, patients, orders and other documents. It is written for the product owner, because mistakes in these three areas, a wrong day, a wrong rupee or a duplicate number, are the ones that clinics notice first. The chapter states the rules, where they are followed strictly, and where the code still departs from them.

62.1 Clinic time

Status: [Implemented] for the rule. [Partial] for coverage: some jobs and statistics still use the server clock.

The rule. Every clinic date and time follows the location's timezone (the timezone of the location, for example a Pakistan or a Gulf timezone). Working hours, appointment availability, the same-day duplicate check, the queue's day boundary, token days and quiet hours all use it. A clinic in one timezone and a server in another still agree on what "today" means for the clinic.

How it works. ClockService is the single source of "now" and "today" for clinic logic. Its main functions are:

  • now(): the current instant (tests can replace it).
  • timezoneFor(locationId): the location's timezone name, defaulting to UTC when the stored name is not valid, cached for 60 seconds.
  • today(timezone): the location-local date as YYYY-MM-DD.
  • wallClock(timezone, instant): the local weekday and HH:MM.
  • dayRange(timezone, date): the start and end instants (in UTC) of a local day.
  • at(timezone, date, time): the instant when the clinic's wall clock reads a given date and time.

The code rule is: never use new Date() together with setHours() for a clinic day or time, because those use the server's timezone. Appointments, queue and notifications follow it (Chapters 29, 30 and 59).

Where the server clock is still used. These places do not use the location's timezone:

  • Scheduled jobs. Daily and monthly jobs run on the worker's server timezone, for example the 01:00 credit expiry, the 02:30 billing check, the 08:00 inventory alert and the payroll run at 05:00 on the 1st (Chapter 63 and Appendix E). The queue's day-end job is an exception: it decides what a past clinic day is from each location's policy.
  • Credit expiry. The check works out "today" from the server's local date, so a prepaid credit can expire a few hours early or late for a clinic in another timezone.
  • Statistics. The financial summary takes its default date and its month list from the server date.
  • Numbering years. The year inside purchase order and prescription numbers is the server's year.
  • Leave balance year uses the server year.
  • The lab catalog calendar fixes its "today" to one specific timezone (Asia/Karachi) regardless of the location.
  • Exports that print a date (patient export file name) use the server date.

For a clinic whose timezone differs from the server's by a few hours, the differences matter only near midnight or at month boundaries.

62.2 Money

Status: [Implemented]

What is stored. Money has two storage styles, depending on the module:

Style Where Meaning
numeric(12,2) rupees Patient billing: charges, invoices, payments, refunds, ledger entries Exact decimal with two places
bigint paisa Commissions (rules, entries, settlements, compensation plans), the lab billing tables (invoice, credits, payments), and a few billing fields Whole number of the smallest unit
decimal(10,2) Inventory prices and quantities, payroll records, employee salary on assignments Exact decimal

The table shows the three styles. A paisa is one hundredth of a rupee; "PKR" is the default currency and not a limit. Amounts cross the API as numbers with at most two decimals in the billing module, and as integer paisa in the lab and commission modules.

How it is calculated. All billing math is done in integer paisa so that no floating-point error can creep in. money.ts holds the helpers: toPaisa and fromPaisa, sumPaisa, percentOf and basisPointsOf. A percentage with up to two decimals is turned into basis points (17.5 percent becomes 1750) and applied with exact big-integer arithmetic.

  • Rounding is half up (0.5 paisa rounds to the next whole paisa), the same everywhere, including tax.
  • Splitting. When an amount is shared in proportion (for example tax spread over charges), each share is rounded down and the leftover paisa go to the largest share, so the shares always add up exactly to the total.
  • Database columns are read through transformers: numeric comes back from the database as text and is rounded to two decimals; bigint comes back as text and is converted to a number, which is exact for any clinic amount.

Figure 62.1 — How an amount typed by a person travels to the database and back.

The flowchart reads top to bottom. A user types 4500.50. The web app converts the text to 450050 paisa with integer-only code (no floating point). The API receives the amount as rupees or paisa depending on the field. Server code calculates in integer paisa with half-up rounding. The value is stored in the database as numeric or as bigint paisa. When the screen reads it back, the web app formats it with the organization's currency.

Tax is exclusive. Prices are before tax. Tax equals the taxable amount (the sum of active charge net amounts after discounts) times the rate, rounded half up once per invoice. The total is subtotal minus discount plus tax. The rate is copied onto the invoice when it is issued from the location's billing settings, and later edits use that copy, not the current setting. Tax is spread over the invoice's charges so that payments can be allocated charge by charge; tax is never revenue and never earns commission. Lab invoices use the same half-up rounding and keep tax in its own paisa column.

Currency. Each organization has a currency (default PKR). It is returned with the organization list after sign-in. The web app's activeCurrency() and useCurrency() read it, and formatPaisa writes amounts as "PKR 4,500.50". Number grouping uses a Pakistani locale. The currency is a display label: there is no conversion and no multi-currency ledger.

62.3 Document numbering

Status: [Partial]. Billing and lab documents are numbered safely; some older numbers are not.

There are four numbering families.

Family Documents Format How it counts
Per location, per type, per year Patient invoices (INV), receipts (REC), refunds (RFD) location code, type, year, five digits, for example MAIN-INV-2026-00001 Table document_sequences
Per organization sequence Lab order (LAB), shipment (SHP), lab invoice (LINV), lab receipt (LRC), payment reversal (LRV), credit note (LCN), lab refund (LRF), vendor bill (VB), vendor payment (VP) prefix and at least four digits, for example LAB-0001 Table number_sequences
Count plus one in application code Patient number, treatment plan number, patient-page prescription number P-00001, TP-00001, RX-00001 Number of existing rows plus one
Last number plus one in application code Purchase order number, prescription number from the prescriptions module PO-2026-00001, RX-2026-00001 Reads the latest row and adds one

The table lists the four families with their formats. Invoices, receipts and refunds need the location's document code (2 to 6 letters or digits, set in billing settings and locked after the first invoice); without it the Platform refuses to issue the document.

The safe families. The first two families use a database counter row that is locked until the surrounding transaction ends. Concurrent requests wait their turn, no number repeats, and a rollback gives the number back, so numbers have no gaps. The service refuses to run outside a transaction. Invoice sequences restart each year, per location. Lab sequences never restart.

The risky families.

  • Patient, plan and prescription numbers (count plus one). The next number is the count of rows for the organization plus one. Two registrations at the same moment can compute the same number, and the second save fails on the unique index. Patients are deleted permanently, so after a deletion the count drops and the next number can repeat one that is still in use (the patient count includes soft-deleted rows but not permanently deleted ones). The result in either case is a failed save that the user sees as a generic error, not a wrong document.
  • Purchase order and prescription numbers (last plus one). The next number reads the most recent row of the organization and adds one, with the year taken from the server clock. Two simultaneous requests can read the same row. In addition, the unique index on the purchase order number and on the prescription number covers all organizations together, so two clinics that both reach the same sequence in the same year would collide.

These are reliability risks, not security ones. A collision stops the save; it does not issue a duplicate.

62.4 Limitations and known gaps

  • Several jobs and statistics use the server timezone, not the clinic's.
  • Two storage styles for money (decimal rupees and integer paisa) exist side by side; conversion happens at module boundaries.
  • Count-based and last-number-based document numbers can collide under concurrency, and purchase order and prescription numbers are unique across all clinics together.
  • No multi-currency support or conversion.
  • Tax is exclusive only; there is no tax-inclusive pricing.

62.5 Owner's FAQ

What time does "today" mean for my branch? The branch's own timezone, set on the location.

Why can a daily job run at an odd hour for my clinic? Jobs follow the server's timezone. A job set for 01:00 runs at 01:00 server time.

Can an invoice number repeat? No. Invoice, receipt and refund numbers come from a locked counter per branch and year.

Can two patients get the same patient number? The database refuses a duplicate, so the second save fails and must be tried again.

Are my prices with or without tax? Without. Tax is added on top at the rate set for the branch when the invoice is issued.

Can I invoice in another currency? You can set the organization's currency label, but there is no conversion.

Chapter 63 — Realtime updates and background jobs

This chapter explains the two ways the Platform acts without a user clicking: it pushes live updates to open screens over a socket connection, and it runs timed jobs and background loops in a worker process. It is written for the product owner who must understand which processes to run and what happens when Redis or the worker is down. Appendix E holds the full job table; this chapter restates the essentials and explains how the pieces fit together. The queue module (Chapter 30) and notifications (Chapters 44 and 59) are the main users of these mechanisms.

63.2 The realtime gateway

Status: [Implemented]

What it does. Pushes small "something changed" messages to open browser screens so that the reception board, doctor screen, waiting-room display and permission-aware screens stay live without constant refreshing.

How it connects. A Socket.IO gateway listens at the path /realtime of the API. The web app connects with websocket transport and passes its access token in the handshake. The token is verified once, when the socket connects. A browser with no token may connect anonymously, but may join only the public display room. After connecting, the client sends a subscribe message naming a room; the server answers with success or a reason.

Rooms.

Room Who may join What it carries
session:<id> Users with access to the queue session's location Events for one doctor's queue (doctor screen, reception)
location:<id>:board Users with access to the location Events of every queue at the location (reception board)
location:<id>:display Anyone, no sign-in Waiting-room TV events; payloads carry token numbers and doctor names, never patient names
org:<id> Users with access to the organization (super admin, owner, or an active staff assignment) The access.changed event with the organization id and the new version

The table lists the four room types. Anything else gets "Unknown room"; a room the user may not enter gets "No access to this room".

Events are nudges. A message carries a sequence number (seq). The browser keeps the sequence of the snapshot it loaded, ignores older or duplicate messages and fetches a fresh snapshot when it sees a newer one. This makes delivery at least once safe, because a duplicate does nothing.

63.3 From a commit to a screen: outbox, relay, Redis

Status: [Implemented]

When a queue action changes state, the same database transaction also writes an event row in the outbox table and sends a database NOTIFY, so an event exists only if the change was committed. The outbox relay in the worker takes unpublished rows (up to 100 at a time, locking them so a second relay would skip them), publishes each to one Redis channel, waits until Redis accepted the whole batch and only then marks the rows as published. If Redis is down, the batch is rolled back and tried again every second. It is woken by the NOTIFY and also polls every second as a fallback. Every API process subscribes to the channel and emits each message to its own local sockets, so a browser connected to any API process sees every event. Chapter 5, section 5.8, shows this as a sequence diagram.

Heartbeat and watchdog. The worker publishes a heartbeat to the same channel every 5 seconds. Each API process runs a watchdog: it considers the bus healthy only while it is subscribed and has seen a heartbeat within 15 seconds. When the bus is unhealthy (Redis or worker down), the API process refuses new socket connections and drops existing ones, using a transport close so that browsers keep trying to reconnect. Screens then fall back to polling about every 10 seconds and reload their data once the socket returns. At start-up the gateway stays closed until the first heartbeat arrives.

Access changes. The access change bus is a second, separate path on its own Redis channel. When an organization's access version is bumped, the bus notifies the local caches and the local gateway, and publishes to Redis so the other processes do the same. Each process then emits access.changed to its sockets in the org:<id> room. This path does not use the outbox or the worker (Chapter 57).

Single-process mode. In the all role, the relay publishes straight to the local gateway.

63.5 Limitations and known gaps

  • Exactly one worker must run; nothing in the code stops a second worker, and a second worker would run each timed job a second time (the relays are safe with several workers, the timed jobs are not guaranteed to be).
  • Job times follow the server timezone, not the clinics'.
  • Inventory alerts reach only the server log, not any user.
  • Realtime depends on Redis in production; without it screens poll about every 10 seconds.
  • The access token is checked once when a socket connects; the connection continues after the token expires.
  • There is no clean-up job for session rows, security logs or the notification outbox.

63.6 Owner's FAQ

What happens if Redis is down? Realtime stops: the API refuses sockets and screens poll every ten seconds, so they update a little later. Access changes still reach the process that made them at once and the others within 15 seconds.

What happens if the worker is down? No timed jobs run, no notifications are sent and no queue events are published. Rows wait in the database and are processed when the worker returns. Screens fall back to polling.

Can I run two workers for safety? No. Run exactly one. A second worker would repeat the scheduled jobs.

Do I need Redis on my laptop? No. The single all process does not need it.

Can the waiting-room TV show patient names? No. The public display room carries token numbers and doctor names only.
