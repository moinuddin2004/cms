How to read this document

This is part of the System Owner's Handbook for a multi-tenant clinic management product, called "the Platform" throughout. It is written for the product owner, a software engineer, and every chapter can be read on its own.

Status labels. Every feature carries exactly one label, based on the code as of 2026-10-28:

  • [Implemented]: built end to end.
  • [Partial]: some of it exists; the text says exactly what is missing.
  • [Not implemented]: planned, seeded, disabled or only mentioned. It is never described as working.
  • [Unverified]: the code was read but the behaviour could not be confirmed; the text says what is unconfirmed.

Source of truth. The code is the source of truth. Where older documentation disagreed with the code, the handbook follows the code. Nothing was executed while writing: behaviour is described from reading the code.

Figures. Every figure has a number, a caption and a paragraph that describes it in words. Figures captioned "screenshot pending" are placeholders; the paragraph after them describes the screen from the code. The few real screenshots were taken on 2026-10-23 and show a former working name of the product.

Names. "Organization" is one clinic business (the tenant); "location" is one of its branches. File paths and code names appear in a short "Technical references" line at the end of each feature. Example people and places are fictional.

Chapter 64 — Feature Status Matrix

This chapter lists every feature described in the module chapters (28 to 45), the workflow chapters (46 to 55) and the cross-cutting chapters (56 to 63), one row each, with its status label. It is for the owner who needs to know what is really built before promising anything to a clinic. The status of each row was merged from the notes of the chapters and checked against the chapter text; where a chapter and its notes differed, the chapter wins.

64.1 How to read the matrix

Each row has four columns: the chapter number, the feature as a user would name it, the status label and a one-line note. The four labels mean the following.

  • [Implemented]: built end to end. The backend and logic exist and a web screen uses them, or it is a backend-only job by design.
  • [Partial]: some of it exists. The note says what is missing, for example "backend only, no screen calls it".
  • [Not implemented]: planned, seeded, commented out or only mentioned. It must not be described as working.
  • [Unverified]: the code could not confirm it. The note says what could not be confirmed.

The workflow chapters (46 to 55) follow one business process across several modules, so many of their rows restate a feature that already has a row in a module chapter. They are listed separately so that each workflow can be judged on its own, and the totals in Section 64.5 report modules, workflows and cross-cutting chapters separately to avoid counting the same feature twice. No application was run while the handbook was written, so every label comes from reading the code.

Chapter 65 — Known Gaps

This chapter collects every gap found while the handbook was written: features that do not exist, features that exist in the backend but cannot be reached from the web app, settings that do nothing, data-integrity oddities and places where older documents describe something the code no longer does. It is for the owner who has to decide what to fix, build or promise before more clinics go live. Each gap states what it is, why it matters to an owner, which chapter holds the evidence, a severity and a suggested next step.

65.1 How severity is judged

Severity is judged by the effect on a live clinic, not by the effort to fix it.

  • High: the problem can stop daily work (registering a patient, writing a prescription) or put the business at risk, and it can happen in normal use.
  • Medium: a clinic would notice and need a workaround, or an expectation set by the product screens is not met, but daily work continues.
  • Low: a convenience, a cleanup or a feature most clinics can live without.

No application was run while the handbook was written, so every gap was found by reading the code. Where a gap depends on behaviour that was deduced but not observed, the text says so.

66.4 Compliance-sounding observations

These are observations, not legal conclusions. A clinic or a regulator may ask about them; the Platform makes no compliance claim, and earlier screenshots that showed such claims were excluded from the handbook.

  • No retention policy. Nothing purges or archives old sessions, security logs, audit rows, notification messages or consent signatures. Network addresses and browser strings are kept indefinitely.
  • Audit coverage is partial. Patient records, billing, prescriptions and queue events keep history. Appointments, employees, payroll, organizations and locations do not, and there is no organization-wide viewer.
  • No row-level security. Tenant isolation is application-level only. The queue sets database session values for tenant and location, but no database policy uses them.
  • Patient documents on external storage. Documents, insurance images and prescription PDFs are stored with an external provider and referenced by address. Access to those addresses is not decided by the Platform's permissions.
  • Consent signatures inside the database. Signature images are stored inline in the consent row, and immutability of consents is a convention, not a database rule.
  • Message text in logs. The stand-in delivery provider writes message bodies and recipient addresses to the application log, which would be unsuitable once real patient channels are switched on. Outbox rows also keep rendered text.
  • No second factor or lockout. Accounts rely on a password with a short minimum.

66.6 What to fix first

Fix the committed credentials first: rotate them and remove the files from history, because the exposure already exists.
